# 收银渠道合规编排

支付平台收银渠道编排后端。统一登记银行卡、余额、消费信贷、资管（货币基金）、
分期等资金来源的**法律类别、提供方资质、适用商户（MCC）与生效区间**；按政策
版本向客户端返回收银台分组、顺序、必要风险信息与可选状态；营销素材另走审核链；
支付与渠道回执全程留痕，供审计复原。

核心合规原则：

- **“可用于付款” ≠ “可混同展示” ≠ “可营销”**。新规生效后消费信贷与货币基金
  仍可付款，但与银行卡/余额分组隔离，且不得在支付链路营销；
- **服务端永不预选**：方案中每个选项 `selected` 恒为 `false`，扣款只接受用户
  在当次会话中的明确选择；
- **灰度不能绕开地区与生效日**：版本解析顺序为 地区/时间校验 → 灰度分桶，
  未命中灰度的用户继续使用旧全量版本；
- **缓存到期即失效**：方案缓存 TTL 被政策与资金源生效区间边界截断，政策发布、
  灰度提升、资金源冻结/上下线都会主动清空缓存；
- **支付重试沿用用户已选渠道并重新核验可用性**，核验不通过只阻断、不静默换渠道；
- **并发发布只有一个有效版本**：发布走 CAS 乐观锁，同地区、同放量阶段的生效
  区间不得重叠；灰度提升（promote）是唯一允许的版本交接路径，新版本在其地区
  确定性遮蔽旧版本。

## 目录结构

| 路径 | 职责 |
| --- | --- |
| `checkout/models.py` | 法律类别、提供方资质、生效区间、时间工具 |
| `checkout/policy.py` | 政策版本存储：地区/生效区间/灰度、CAS 发布、唯一有效版本 |
| `checkout/catalog.py` | 资金源与提供方登记、资质校验、运行时可用性核验 |
| `checkout/orchestrator.py` | 收银台方案编排（分组/顺序/风险信息/可选状态/禁止预选）与边界缓存 |
| `checkout/marketing.py` | 营销审核链（禁用词、保本暗示、首期费用、优惠诱导、支付导流） |
| `checkout/payments.py` | 显式选源、每次重新核验、同渠道重试、幂等 |
| `checkout/ledger.py` | 只追加事件台账、外部回执归类（错误分类/迟到确认）与审计复原 |
| `checkout/app.py` | 装配与夹具加载 |
| `checkout/api.py` | 标准库 HTTP 路由 |
| `fixtures/` | 三版政策、6 个资金源/6 家提供方、跨 9·30 的渠道回执 |

## 政策时间线（fixtures）

- **v1（2017 试行规则）**：全地区全量，持续至 `2026-10-15`；信贷/理财可与
  银行卡同屏、可营销，营销规则只含禁用词与保本暗示；
- **v2（2026 新规）**：`2026-09-30 00:00 (CST)` 起在**上海 20% 灰度**，
  金融产品各自独立分组、必须展示风险信息、不可营销，还款页/支付结果页禁投；
- **v3（2026 新规全量）**：`2026-10-15 00:00 (CST)` 起全国全量。

灰度期上海未命中分桶的用户继续看到 v1 方案；北京等其他地区始终是 v1，
直到 v3 全国生效。

## 运行

```bash
pip install -r requirements.txt
python3 service.py --check        # 配置自检（政策区间、资金源、回执）
python3 service.py --port 8000    # 启动服务
python3 -m pytest -q              # 90 个测试
```

## HTTP 接口

| 方法/路径 | 说明 |
| --- | --- |
| `GET /health` | 服务身份 |
| `GET /checkout?order_id=&region=&mcc=&at=&user_id=` | 生成收银台方案（并登记呈现事件） |
| `POST /checkout/select` | 登记用户明确选择（无默认勾选） |
| `POST /payments/attempt` | 首次扣款（必须先选择；扣款时重新核验） |
| `POST /payments/retry` | 同渠道重试（重新核验，失败不静默换源；支持幂等键） |
| `POST /marketing/review?region=` | 素材审核，阻断时逐条返回规则、条款、命中片段与位置 |
| `GET /policies?region=&at=&user_id=` | 版本解析（full/canary/fallback） |
| `POST /admin/policies/publish` | CAS 并发发布（`expected_version`） |
| `POST /admin/policies/{v}/promote` | 灰度提升全量（CAS） |
| `GET /audit/orders[/{id}]` | 按订单复原布局、选择、政策来源、扣款与回执异常 |

## 回执与审计

`fixtures/receipts.jsonl` 横跨 9 月 30 日，包含：

- 9-29 旧规下的信贷支付（迟到 3 天的成功确认）；
- 10-01 上海灰度新规下银行卡支付，失败后**同渠道重试**成功（迟到确认）；
- 10-02 货基支付后，一条被错误标记为 `ad.click.attribution`、且状态与原扣款
  矛盾的迟到确认（`misclassified` + 状态矛盾 finding）；
- 一条幽灵风控回调（错误分类、非法状态、无对应扣款尝试）。

台账不丢弃任何回执：原始声明类型保存在 `declared_type`，归类结果与异常
（`misclassified` / `late-confirmation` / `bad-status` / `duplicate-confirmation`
等）逐条记录；审计把「迟到但事实一致」列为 notices，把状态矛盾、无扣款的幽灵
确认、服务端预选、重试换渠道等列为 findings。

仓库不保存真实账户、余额或交易凭据。
